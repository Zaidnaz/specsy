# specsy dry run — 0.2.1

**Date:** 2026-09-13
**Under test:** specsy 0.2.1 (local build, `node dist/cli.js`)
**Target project:** `finance-tracker` — a greenfield TypeScript/Node personal finance
tracker with one in-flight OpenSpec change (`add-core-ledger`: 3 capability specs, 19
requirements, ~60 scenarios, 23 tasks).

The global install on this machine was still `0.1.1`, so every command below was run
against the repo's own `dist/` build rather than the `specsy` shim on `PATH`. Worth
knowing if you reproduce this: `specsy --version` and `node dist/cli.js --version` did
not agree.

---

## 1. Regression checks

Three defects were reported against 0.1.1 earlier in this session. All three are fixed in
0.2.1 (`db0e2d7` — *"0.1.4: correct line numbers, and two false positives"*). Each was
re-tested against a minimal fixture rather than taken on trust.

### 1.1 Line numbers were off by one

Fixture — `robust` is on **line 9, column 25**:

```
$ grep -n "robust" specs/t/spec.md
9:The system SHALL handle robust inputs.

$ node dist/cli.js "$FIXTURE" --format generic
  9:25   warn  "robust" is not measurable.  no-weasel-words
```

**Fixed.** 0.1.1 reported `8:25` — column right, line one short. Confirmed against four
separate findings at the time, across both `no-weasel-words` and
`one-requirement-per-statement`, which pointed at the shared requirement-body line mapping
rather than either rule. 0.2.1 reports the true position.

### 1.2 CLI metavariables read as unfinished placeholders

Fixture containing both the false positives and one genuine placeholder:

```markdown
### Requirement: FP-001 CLI metavariables

The tool SHALL accept `--scope <name>` and `--change <id>` as options.
The report SHALL state how many documents the run covered.

### Requirement: FP-002 A real placeholder should still be caught

The tool SHALL do TBD once the decision is made.
```

```
$ node dist/cli.js "$FIXTURE" --format generic
  19:19  error  Unfinished spec: "TBD".  no-placeholders

✖ 1 problem (1 error, 0 warnings) in 1 document(s).
```

**Fixed, and fixed correctly.** In 0.1.1, `` `<name>` `` and `` `<root>` `` in inline code
spans raised *"Unfinished spec"* **errors** — enough to fail a build for anyone documenting
a CLI. They are now silent. The important half is the second requirement: a real `TBD`
still errors, at exactly `19:19`. The false positives were removed by narrowing the rule,
not by weakening it.

### 1.3 `"how many"` tripped the weasel word `many`

Same fixture, line 10: `The report SHALL state how many documents the run covered.`

**Fixed.** No finding. Previously flagged as *"many" is not measurable*.

### 2.3 `explain`

```
$ node dist/cli.js explain one-requirement-per-statement

one-requirement-per-statement  (warn by default)

Splits requirements that bundle several obligations into one line.
Applies to: spec.

Why:    Two obligations in one sentence cannot be tested, traced, or partially satisfied independently.

Fails:  The system MUST validate the currency and MUST reject amounts of zero.

Passes: The system MUST validate the currency.
        The system MUST reject an amount of zero.

Turn it off with {"rules": {"one-requirement-per-statement": "off"}} in .specsyrc.json.
```

The strongest addition in 0.2.x. A failing example, a passing one, the reason, and the
exact escape hatch. This is the rule teaching its convention rather than only enforcing it,
which matters because the author of a vague requirement is the person least able to see it.

## 3. Finding: the CLI and MCP surfaces disagree

`lint_specs` accepts a `change` argument. The CLI has no equivalent, and neither
`specsy openspec/changes` nor the `ignore` config key can stand in for it:

```
$ node dist/cli.js openspec/changes
No spec format detected in "E:\projects3\open_spec_prj\openspec\changes".
```

`specRoot()` looks for a `changes` directory beneath the given path, or `openspec/changes`
beneath it; the changes directory itself contains neither.

So **an agent driving specsy over MCP can narrow a run; a human or a CI job driving the
same tool from the command line cannot.** Two consequences in the current implementation
(`src/mcp/server.ts:70`):

```ts
const selected = change
  ? { ...project, changes: project.changes.filter((c) => c.id === change) }
  : project;
```

- It filters **after** `loadProject`, so every markdown file in the living spec is read and
  parsed purely to be discarded.
- It matches `c.id`, and the living spec is a pseudo-change whose id is the display string
  `(living spec)` — so that string is selectable as a change id today.

This is the subject of the `add-lint-scoping` change proposal in `openspec/changes/`, which
has been updated to account for it.

## 4. Improvements still worth making

Ordered by how likely each is to bite a real user. Items 1–3 were found by probing rather
than by reading code, so each has a reproduction.

### 4.1 A misspelled rule id in `.specsyrc.json` is silently ignored — *high*

```json
{ "format": "generic", "rules": { "no-weasle-words": "off" } }
```

```
$ node dist/cli.js .
  9:25   warn  "robust" is not measurable.  no-weasel-words
▲ 1 problem (0 errors, 1 warning) in 1 document(s).
```

The user asked for a rule to be off, the rule fired anyway, and nothing said why. This is
the same class of silent failure specsy exists to catch in specs, occurring in specsy's own
config. Validating keys against `allRules` and reporting an unknown one — with a
did-you-mean, since `rules` already knows every id — would close it. Worth deciding whether
that is a warning or a hard exit 2; given the config is a deliberate statement of intent, I
would make it exit 2.

### 4.2 An unknown `--reporter` silently falls back to pretty — *medium*

```
$ node dist/cli.js . --reporter nonsense   # prints pretty output, exit 0
$ node dist/cli.js . --format nosuchformat # exit 2, names the known formats
```

`--format` gets this right and `--reporter` does not. A CI job asking for
`--reporter github` and receiving pretty output would lose its annotations with no
indication anything was wrong.

### 4.3 `config.ignore` is dead — *medium*

Declared on `Config`, defaulted in `defaultConfig`, merged in `resolveConfig` — and read by
no adapter, rule, or scan. It reads like a working feature to anyone inspecting the type.
Either implement it or remove it; leaving it is the worst of the three.

### 4.4 The living spec is identified by a display string — *medium*

`(living spec)` is simultaneously the label shown to users and the key filtering matches
on. Renaming the label silently changes behavior, and it is already selectable as a change
id over MCP. A `kind: "change" | "living"` field on `SpecChange` separates identity from
presentation. Covered by `add-lint-scoping`.

### 4.5 `quantify-performance` defaults to `error` — *low, opinion*

It matches bare adjectives (`fast`, `responsive`, `real-time`). An error default means a
sentence like "a fast path through the cache" fails a build. `warn` seems truer to the
confidence the rule can actually have; `--max-warnings 0` is available to anyone who wants
it strict.

### 4.6 The documented exit codes are slightly imprecise — *low*

Help says `0 clean   1 findings   2 specsy could not run`. Measured:

| Situation | Exit |
|---|---|
| No findings | 0 |
| Warnings only, no `--max-warnings` | **0** |
| Warnings over `--max-warnings` | 1 |
| One or more errors | 1 |
| Unknown `--format`, unknown `explain` rule, nothing found | 2 |

Warnings are findings but exit 0, so `1 findings` overstates it. Something closer to
`1 errors (or warnings over --max-warnings)` would prevent someone wiring CI on the wrong
assumption.

### 4.7 Smaller notes

- The JSON reporter already emits `documentCount`, but the pretty summary is the only place
  a reader learns how much was actually checked. Once scoping lands, both need the active
  scope too, or a narrowed run reads identically to a full one.
- `requirements-have-tasks` no-ops when a change has no tasks document. That is the correct
  behavior, but it means a change consisting only of specs looks fully covered.
- There is no `specsy init` to scaffold `.specsyrc.json`. Minor, but it would be a natural
  place to surface the recommended per-project settings.

---

## 5. Overall

The three defects reported against 0.1.1 are fixed, fixed narrowly, and verified by
reproduction rather than by changelog. The rule engine is in good shape: a real project's
specs pass cleanly, and the one rule that fired against my own writing during this session
(`one-requirement-per-statement`) caught three genuine bundled obligations I had written
*despite* the convention being mine.

The weak points that remain are not in the rules. They are in the edges around them —
config keys that are accepted and ignored, an option that falls back instead of failing,
and two surfaces that disagree about what the tool can do. Each is the same shape: a silent
wrong answer where a loud refusal belongs, which is precisely the standard the rules
themselves hold specs to.

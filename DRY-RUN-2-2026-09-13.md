### 1.1 §4.1 — misspelled rule id in config *(was: silently ignored)*

```
$ cat .specsyrc.json
{ "format": "generic", "rules": { "no-weasle-words": "off" } }

$ node dist/cli.js .
Invalid config in ...\.specsyrc.json:
  Unknown rule "no-weasle-words". Did you mean "no-weasel-words"?

A config file is a statement of intent, so specsy refuses rather than ignoring it.
exit=2
```

**Fixed**, including the did-you-mean. Validation went further than reported — three cases
I had not raised are also refused:

| Config | Message | Exit |
|---|---|---|
| `"weaselWord": ["foo"]` | `Unknown setting "weaselWord". Known settings: format, ignore, rules, weaselWords.` | 2 |
| `"rules": {"no-weasel-words": "loud"}` | `Rule "no-weasel-words" has severity "loud". Use "error", "warn" or "off".` | 2 |
| `"weaselWords": "foo"` | `"weaselWords" must be an array of strings.` | 2 |
| Malformed JSON | `Failed to read ...: Expected double-quoted property name at position 24` | 2 |

Listing the known settings in the unknown-key message is the right touch — it turns a
rejection into a discovery path.

## 3. New findings

Three of the five below are the same shape as everything 0.2.2 fixed: input accepted, then
quietly not honoured. That the theme survived in paths the release didn't cover is the main
result of this run.

### 3.1 `ignore` can exclude everything and the run reports success — *high*

```
$ cat .specsyrc.json
{ "format": "generic", "ignore": ["**"] }

$ node dist/cli.js .
✔ No problems in 0 document(s).
exit=0
```

A config that excludes every document exits 0 with a green tick. In CI this is a gate that
passes because it checked nothing — the precise failure the newly-implemented `ignore` key
makes reachable for the first time, and the exact case `add-lint-scoping` specifies as
`SCOPE-003` for scope selections.

The information is already on screen (`0 document(s)`), so this is only about the verdict
attached to it. Same treatment as the config errors would fit: refuse, exit 2, say that the
selection covered nothing. Note the pre-existing `No spec documents found in "..."` path
already exits 2 — so an empty *project* is an error while an empty *selection* is a success,
which is hard to justify.

### 3.2 `--quiet` silently disables `--max-warnings` — *high*

```
$ node dist/cli.js . --max-warnings 0            # 2 warnings present
exit=1

$ node dist/cli.js . --quiet --max-warnings 0    # same 2 warnings
exit=0
```

`--quiet` switches every `warn`-severity rule to `off`, so by the time `--max-warnings` is
evaluated there are no warnings left to exceed the threshold. The combination reads as
"strictest possible" and behaves as "warnings not checked at all".

This is literally accepting input it then ignores: `--max-warnings 0` is parsed, has no
effect, and nothing says so. Either refuse the combination, or have `--quiet` affect only
*display* while severity and exit code still count the warnings. The second is probably what
a user means by "report errors only".

### 3.3 The generic adapter invents a change id — *medium*

```
$ cat .specsyrc.json                     # generic layout, no changes concept
{ "format": "generic" }

tools/call lint_specs {"format":"generic","change":"anything"}
→ No change named "anything". Available: dr2.
```

`dr2` is the fixture's directory name. The generic adapter has no notion of an in-flight
change, but the whole project is presented as one, so the refusal message teaches a user a
concept their layout does not have — and `change: "dr2"` would "work" while narrowing
nothing. `add-lint-scoping` specifies this as `SCOPE-004` (an adapter that cannot honour a
change-based selection should refuse it), and `Adapter.hasChanges` is the field that would
carry it.

### 3.4 `footprint` still counts the living spec as a change — *low*

```
$ node dist/cli.js footprint
(living spec)  60 tokens
Total 233 tokens across 2 change(s)
```

One change plus a living spec is reported as "2 change(s)". `SpecChange.kind` landed in
0.2.2, so the distinction now exists in the model and just hasn't reached this reporter.
Cosmetic, but it is the same label-versus-identity confusion §4.4 fixed elsewhere.

### 3.5 An `ADDED` requirement may collide with the living spec — *low, new rule idea*

A delta under `## ADDED Requirements` declaring an id that already exists in the living
spec is not flagged. Reusing an id under `## MODIFIED Requirements` is correct and must stay
silent, so the rule would have to key off the delta operation heading — which is why this is
an idea rather than a defect. The payoff is real though: an `ADDED` id that already exists
is a collision that surfaces at archive time, when it is most expensive to untangle.

## 4. Status of `add-lint-scoping`

Still unimplemented, and correctly so — `scope` does not appear in
`Known settings: format, ignore, rules, weaselWords`. Two of its requirements were
partially delivered by 0.2.2 as side effects:

- `SCOPE-002` — the living spec is no longer selectable as a change id. Done.
- `SCOPE-004` — `Adapter.hasChanges` does not exist yet; §3.3 above is that gap observed
  from the outside.
- `SCOPE-003` — §3.1 above is the same requirement, reached through `ignore` instead of
  through scope. Whichever lands first should own the shared "selection covered nothing"
  path rather than each growing its own.

The commit message notes `SpecChange.kind` "unblocks the add-lint-scoping proposal", which
matches: that field was the prerequisite the design called out.

## 5. Overall

Six of six items from dry run 1 are fixed, verified by reproduction, and three of them were
fixed more thoroughly than reported — the config validator covers cases I never raised. No
regressions: both real projects still lint clean, and the rule engine was not disturbed.

The pattern worth naming across both runs: the rules are sound, and every defect either run
has surfaced has been in the *edges* — config keys, flag combinations, adapter vocabulary,
exit codes. §3.1 and §3.2 are the same bug the release was named after, reached through two
paths it didn't close. That is not a criticism of the fix; it suggests the check is worth
making structural. A single question asked once — *did this run actually examine anything,
and did every input the user supplied change the outcome?* — would have caught §4.1, §4.2,
§3.1 and §3.2 in one place.
